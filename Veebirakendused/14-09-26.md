## 🗂️ Topics Covered

### 1. 📜 JavaScript, ECMAScript & Why There Are Two Names

The session opened with where JavaScript actually comes from. The language is standardised
under the name **ECMAScript**: JavaScript is the implementation, ECMAScript is the spec that
a standards body maintains.

The version history explains a lot about how the language feels today:

| Version | Year | Note |
|---|---|---|
| ES5 | 2009 | The long-lived baseline. Everything supported it. |
| ES6 / ES2015 | 2015 | The huge one: the modern language starts here |
| ES2016 → today | yearly | Small, incremental releases |

**The key point:** after ES6 the committee switched to **small yearly releases** instead of
saving up a decade of changes. Big-bang releases meant a massive pile of features landing at
once and browsers taking years to catch up. Small releases mean less of a gap between "the
spec has it" and "you can actually use it".

> 💡 A language feature existing is worthless if no browser implements it. ES5 took roughly
> 5 years to become genuinely usable; ES6 was faster; modern yearly additions are faster still.

**On browser support today:** you effectively only need to worry about **three engines**, not
a long list: Chromium (Chrome, Edge, Opera, Brave), Firefox, and Safari. Mobile is mostly a
non-issue now.

### 2. 🔄 Transpilers: Writing Modern Code for Old Browsers

If the browser doesn't support the syntax you want, you run your code through a tool that
rewrites it into something the browser *does* understand. That tool is a **transpiler**.

**Babel** was the classic answer: write the newest JavaScript, run it through Babel, ship
something an older browser can execute.

**Why it matters much less now:** browsers have caught up. You mostly only reach for this if
you must support genuinely ancient devices: the example given was old handheld/industrial
terminals still running some fossil browser. Otherwise, don't invent work for yourself.

> 📌 **Terminology:** *compiling* usually means source → machine code. Going from one
> human-readable language to another human-readable language is **transpiling**
> (trans + compile).

### 3. 🛡️ TypeScript: Types as Safety Rails

TypeScript is JavaScript **plus a type system**. It is arguably as popular as plain JavaScript
now, and it was framed here in terms of *typed vs untyped* languages.

**The core idea:**
- In untyped JS, a function takes whatever you hand it and hopes for the best
- In TS, you declare what a parameter is (a string, a number, a specific shape) and the
  tooling enforces it

**Why bother with the extra ceremony:**
- Alone on a small school project? You'll probably remember what your own function expects.
- On a bigger project, months later, or on a team of 3–4 people? You will not.
- You constantly call functions **you did not write**. Types are how that code tells you what
  it wants, before you run it.

**The catch:** the browser cannot read TypeScript. So TS ships with a tool that type-checks
your code and then **strips the types out**, emitting plain browser-edible JavaScript: the
same transpiling idea as Section 2.

### 4. ☕ CoffeeScript: A Historical Note

CoffeeScript was covered as the **opposite** design goal to TypeScript:

- **TypeScript** adds ceremony to gain safety
- **CoffeeScript** removed ceremony to gain brevity: shorthand syntax, less punctuation,
  compiled down to plain JavaScript

**Why it's no longer worth learning:** most of its good ideas were absorbed into modern
JavaScript itself. Today's JS is already short enough that CoffeeScript's advantage mostly
evaporated. Shown for context, not for use.

### 5. 🎨 Sass: The Same Trick, but for CSS

The exact same pattern appears in CSS: write in a nicer language, compile down to what the
browser accepts. There are several CSS preprocessors; **Sass** is the popular one.

**What Sass gives you:**
- **Variables**: define a colour once, use it everywhere
- **Nesting**: structure that mirrors your markup
- **Splitting into multiple files**: keep things organised, compile to one output
- **Functions / mixins**: stop writing the same block of CSS repeatedly, with or without
  parameters
- **Colour functions**: derive colours from each other, e.g. "the hover state is this colour
  but 15% lighter". Change the base colour and everything derived from it updates.

**Sass variables vs CSS custom properties: an important distinction:**

| | Sass variable | CSS variable (custom property) |
|---|---|---|
| When is it resolved? | **Once, at build time** | **Every time, in the user's browser** |
| Cost to the user | None: output is plain CSS | The browser recalculates on change |
| Can change at runtime? | No | Yes |

The performance argument: one recalculation is nanoseconds: irrelevant. But multiply it by
ten million page views and it stops being free. Sass does the maths once on your machine (or
at deploy) and ships finished, static CSS.

> ⚖️ This is not "CSS variables are bad": they do something Sass fundamentally cannot
> (change at runtime). It's about knowing which tool is doing work *when*.

### 6. 📦 Build Tools & Bundlers: Vite

Once you have a transpiler, a CSS preprocessor, a type checker and a handful of other tools,
you need something to **run them all together**. That's a bundler.

**Vite** was named as the current popular choice: it orchestrates all those tools and outputs

### 7. 🚀 Runtimes: Node, Deno & Bun

Everything so far runs in a browser. At some point people wanted JavaScript **outside** the
browser: on the server, reading files, creating servers, doing ordinary programming work.

**Node.js** was the answer and became the default.

**Deno**: built by the *original author of Node*, as a second attempt. The motivation: when
you build something the first time you don't get everything right, and once a platform is huge
you can't fix early decisions without breaking the world. Deno's problem was that it initially
**didn't support npm**, which meant rewriting every existing project, so adoption stalled.
It has since added npm compatibility, but by then there was competition.

**Bun**: the one the instructor is currently using. Selling points covered:
- **npm-compatible from the start**: existing Node projects should just run
- **Fast**: it's written in Zig; the benchmark claims are, as always, to be taken with salt
- **Batteries included**: things you'd normally pull in as separate packages (drivers, assorted
  utilities) are built in, so fewer dependencies
- **Runs TypeScript directly**: no separate build step to execute a `.ts` file
- **Can bundle an app or server into a single binary**: ship one file, no runtime required

> 🧠 All three are broadly interchangeable for ordinary work: `node x.js`, `deno x.js`,
> `bun x.js`. Learn the concepts and you can move between them.

### 8. 🔧 Hands-On: Setting Up the First Project

The last part of the session was everyone setting up a project from scratch.

**Step 1: Configure Git (once per machine, not per project):**
```bash
git config --global user.name "Your Full Name"
git config --global user.email "your.email@example.com"
```
> ⚠️ This is the step that always gets forgotten. It is **per computer**, not per project:
> it does not matter which directory you run it in. Ideally use the same email as your
> GitHub account.

**Step 2: Make a project directory and open it:**
```bash
mkdir ta25afront
cd ta25afront
code .
```

**Step 3: Initialise the repository.** A repo needs at least one file to commit: a
`readme.md` is the usual choice. It doesn't have to be elaborate, but anything you'll want to
know later belongs there, because it stays with the repo forever.

**Step 4: Create the repo on GitHub** and connect it. Public repository.

**Step 5: `bun init`** to scaffold the project.

**Step 6: Convert from TypeScript to JavaScript.** The scaffold starts as TS; for this course
it was converted down to plain JS (`tsconfig.json` removed, `index.ts` → `index.js`).

**Step 7: Add an `index.html` and a file-reading example.**

**Verifying Bun is installed:**
```bash
bun --version
```

## ✅ Takeaways

1. **JavaScript = the language, ECMAScript = the standard.** Yearly releases replaced the
   decade-long gaps.
2. **Transpiling is a recurring pattern**, not one tool: Babel does it for new JS, TypeScript
   does it for types, Sass does it for CSS. Same idea every time: write something nicer,
   compile to what the target accepts.
3. **Types are for the future reader**: your teammates, and you in three months.
4. **Do work at build time, not in the user's browser**, when you have the choice.
5. **Node, Deno and Bun are interchangeable enough** that the concepts transfer. Learn one well.
6. **`git config --global` is a one-time setup**: do it before your first commit, not after.
